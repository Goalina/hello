# 错误报告：vllm-deepseek-v3-1-bf16-efe9f2 Pod CrashLoopBackOff **简要结论**：PR #13480 将镜像依赖的 CANN 版本从 9.0.1 升级到了 9.1.0，但多机测试的启动脚本 `run.sh` 里有一行路径写死了 `cann-9.0.1`，没有同步更新，导致 Pod 启动时找不到对应文件，直接崩溃退出。 --- ## 一、现象 ``` vllm-project vllm-deepseek-v3-1-bf16-efe9f2-0 0/1 CrashLoopBackOff 4 (17s ago) 4m14s vllm-project vllm-deepseek-v3-1-bf16-efe9f2-0-1 0/1 CrashLoopBackOff 4 (25s ago) 4m14s ``` 多机测试的 Leader 和 Worker 两个 Pod 均处于 CrashLoopBackOff 状态（即反复启动、崩溃、重启的死循环），退出码为 1。 --- ## 二、报错信息 从 Pod 日志中拿到的唯一一行报错： ``` /root/.cache/tests/run.sh: line 27: /usr/local/Ascend/cann-9.0.1/share/info/ascendnpu-ir/bin/set_env.sh: No such file or directory ``` Pod 启动后第一件事是执行 `run.sh`，脚本在第 27 行试图加载一个环境变量配置文件，但这个文件不存在，脚本立即退出。 --- ## 三、根因分析 ### run.sh 是什么，它在哪 `run.sh`（位于代码仓库 `tests/e2e/nightly/multi_node/scripts/run.sh`）是多机测试的启动脚本，负责配置 NPU 环境变量、从 GitHub 拉取最新代码、启动 vLLM 推理服务、运行测试用例。 每次 CI 跑多机测试时，workflow 会先把这个脚本从代码仓库复制到多台机器共享的存储空间（PVC）上，Pod 启动后再从共享存储里读取并执行： ``` CI workflow ├─ [第1步] 构建镜像，推送到镜像仓库 ├─ [第2步] 把 run.sh 从代码仓库复制到共享存储（/root/.cache/tests/run.sh） ├─ [第3步] 用新镜像拉起多个 Pod └─ [第4步] Pod 启动，执行 bash /root/.cache/tests/run.sh ``` ### run.sh 里写死了旧版本路径 `run.sh` 第 27 行在加载 ascendnpu-ir 的环境变量时，把 CANN 版本号直接硬编码在了路径里： ```bash # 第26行（没问题） source /usr/local/Ascend/ascend-toolkit/set_env.sh # 第27行（问题所在） source /usr/local/Ascend/cann-9.0.1/share/info/ascendnpu-ir/bin/set_env.sh ``` ### PR #13480 升级了 CANN 版本，run.sh 没有同步更新 PR #13480（合并于 2026-08-04 11:29 UTC）将镜像构建依赖的底包日期从 `2026.07.29` 改为 `2026.08.03`： ```yaml # _nightly_image_build.yaml - default: '2026.07.29' + default: '2026.08.03' ``` 这个日期是华为底包镜像仓库 `quay.io/atlas_inference/vllm-ascend` 的 tag，不同日期对应不同的 CANN 版本： ``` cann2026.07.29 → CANN 9.0.1 cann2026.08.03 → CANN 9.1.0 ``` PR 合并后触发镜像重新构建，新镜像（2026-08-04 16:52 UTC）使用了 `cann2026.08.03` 底包，镜像内 CANN 升级至 9.1.0，`cann-9.0.1` 目录完全不存在。本地检查镜像文件系统确认： - `/usr/local/Ascend/cann-9.1.0/` ✅ 存在 - `/usr/local/Ascend/cann-9.0.1/` ❌ 不存在 `run.sh` 开头有 `set -euo pipefail`，任何命令失败立即终止脚本，Pod 退出后 Kubernetes 不断重启，形成 CrashLoopBackOff。 ### 完整崩溃链路 ``` PR #13480 合并（2026-08-04 11:29） └─ 底包日期 2026.07.29 → 2026.08.03，即 CANN 9.0.1 → 9.1.0 ↓ 新镜像构建完成（2026-08-04 16:52） └─ 镜像内只有 cann-9.1.0，cann-9.0.1 目录不存在 ↓ Nightly 测试触发，Pod 启动，执行 run.sh ↓ run.sh 第27行：source .../cann-9.0.1/... ← 路径不存在，命令失败 ↓ set -euo pipefail → 脚本立即退出，exit code 1 ↓ Pod 退出 → Kubernetes 重启 → 再次崩溃 → CrashLoopBackOff ``` --- ## 四、影响范围 本次 CI run 中所有使用 `nightly-ci-main-a3` 镜像的多机测试均受影响： - multi-node-deepseek-v3.1（DeepSeek-V3.1-BF16.yaml） - multi-node-deepseek-v3.2-W8A8-EP（DeepSeek-V3_2-W8A8-EP.yaml） - multi-node-GLM-5.2-w8a8-A3（GLM5_2-W8A8-A3-dual-nodes.yaml） --- ## 五、修复建议 **根本修复**：修改 `tests/e2e/nightly/multi_node/scripts/run.sh` 第 27 行，去掉硬编码的版本号，改用镜像中已有的环境变量 `CANN_VERSION`： ```bash # 修改前 source /usr/local/Ascend/cann-9.0.1/share/info/ascendnpu-ir/bin/set_env.sh # 修改后 source /usr/local/Ascend/${CANN_VERSION}/share/info/ascendnpu-ir/bin/set_env.sh ``` 镜像里已通过 `ENV CANN_VERSION=9.1.0` 注入了版本号，使用该变量后，后续镜像升级 CANN 版本时脚本无需再做任何修改。 **临时修复**：若需要立即恢复 CI，可将第 27 行的 `cann-9.0.1` 直接改为 `cann-9.1.0`，但这只是推后了下一次同样问题出现的时间。 **附加建议**：在镜像构建 workflow 完成后、触发测试之前，增加一个验证步骤，检查 `run.sh` 中所有 `source` 的路径在新镜像内均存在，从流程上杜绝此类镜像与脚本版本脱节的问题。
